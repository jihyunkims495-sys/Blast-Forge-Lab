### 자동화 승인 기준

다음 조건을 모두 충족할 때 우선 검토한다.

- 동일하거나 유사한 작업이 3회 이상 반복됨
- 자동화가 실제 시간을 줄임
- 결과의 성공 여부를 확인할 수 있음
- 사람의 최종 판단이 필요한 부분이 분리되어 있음
- 잘못 실행될 때의 위험이 낮거나 복구 가능함
- 복사·붙여넣기와 왕복 대화를 오히려 늘리지 않음

### 자동화하지 않을 업무

- 일회성 요청
- 정서적·상황적 판단이 중요한 요청
- 잘못 실행되면 법률·재무·건강상 위험이 큰 업무
- 입력 정보가 매번 크게 달라지는 업무
- 자동화 유지 비용이 수작업보다 큰 업무

## 7. 오케스트레이터 도입 판단

### 오케스트레이터의 정의

`00_개인 운영·자동화실`은 프로젝트 이름만 만든다고 01~04의 메모리를 자동으로 읽는 관리자가 되지 않는다.

실제 오케스트레이터가 되려면 다음 세 요소가 필요하다.

1. 각 프로젝트의 결과를 모으는 공용 데이터 공간
2. 공용 데이터를 정기적으로 분석하는 운영 규칙
3. 분석 결과를 바탕으로 개선안을 제안하는 실행 흐름

### 2026-08-18에 바로 만들지 판단하는 기준

아래 항목 중 `예`가 3개 이상이면 구체적인 설계를 시작한다.

- [ ] 01~04 중 3개 이상을 실제로 사용했다.
- [ ] 프로젝트 간 결과를 연결해야 하는 일이 3회 이상 발생했다.
- [ ] 같은 정보를 여러 프로젝트에 반복 입력했다.
- [ ] 공용 주간 리포트가 실제로 필요하다고 느꼈다.
- [ ] 자동으로 모으고 싶은 데이터의 종류와 저장 위치가 명확하다.
- [ ] 복사·붙여넣기 없이 데이터를 모을 현실적인 방법이 있다.
- [ ] 운영실이 줄여줄 시간이 유지·관리 비용보다 크다.

### 도입 보류 기준

다음 중 하나에 해당하면 1~2주 더 사용한 뒤 다시 판단한다.

- 프로젝트별 사용 데이터가 부족함
- 4개 프로젝트 중 실제 사용하는 프로젝트가 2개 이하임
- 프로젝트 간 연결 필요성이 거의 없음
- 공용 데이터를 자동 수집할 방법이 없음
- 사용자가 직접 요약을 복사해야 해서 업무가 늘어남
- 오케스트레이터의 목적이 구체적이지 않음

### 권장 도입 시점

- 가장 빠른 검토 시점: 2026-08-18 1차 피드백 후
- 권장 결정 시점: 실제 사용 2주 후인 2026-08-28 전후
- 즉시 도입 조건: 프로젝트 간 중복 입력과 수작업 전달이 명백하게 반복되고, 공용 데이터 수집 방법이 확보된 경우

### 도입한다면 먼저 결정할 것

1. 공용 데이터 저장 위치: Library / Notion / Slack
2. 각 프로젝트가 남길 주간 요약 형식
3. 운영실이 분석할 항목
4. 분석 주기: 주간 / 격주 / 월간
5. 자동화 실행 전 사용자의 승인 범위
6. 민감 정보와 프로젝트별 전용 메모리 보호 기준
